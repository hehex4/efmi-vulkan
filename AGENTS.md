# EFMI Vulkan - working agreement

- When resuming work, read `.ai-memory/CURRENT_STATE.md` and `.ai-memory/TASKS.md` first; goal, architecture, constraints and earlier decisions are in the other memory documents, and the full plan is `docs/plan.md`.
- Modify only this project, `F:\efmi vulkan`. The one other location this project owns is `F:\vulkan`: whatever the project needs installed (headers, SDKs, tools) goes there directly, without asking first (user, 2026-10-11). The EFMI/XXMI installation, the launcher configuration, `d3d11.dll`, `d3dx.ini`, `Core`, existing mods, the game installation and the sibling project `F:\EFMI MCP` are read-only.
- The layer is never loaded into the real game without the user saying so on the spot. Gate G1 carries a risk for the account, and which account is used is the user's decision. No work is ever done to evade, hide from or fight the anti-cheat; if loading is blocked, the project stops.
- Every bug starts from the original: read how 3DMigoto handles the same situation (`F:\vulkan\XXMI-Libs-Package\DirectX11`), state it in the analysis, and build the Vulkan solution on it, making explicit what DX11's runtime does for 3DMigoto (reference-counted lifetime with deferred destruction, hazard tracking, one context's order) (user, 2026-10-26: do not make me remind you again).
- The work is general, not an adaptation per character (user, 2026-10-19; D-044, D-075): every installed Mod and characters never captured must work through shared mechanisms. Captures are ground truth for building and checking general rules, never per-character tables, packages or profiles the runtime depends on.
- The replacement logic is a module of its own that the loaded layer can exchange while the game runs (user, 2026-10-13). Whether to exchange it in a game the user started is the agent's choice: after changing the replacement logic the agent may swap the new module in to verify it, without asking each time, and says what it swapped. This covers that module only. The agent still does not start or stop the game, the injected DLL and the other deployed files are replaced only while the game is closed, and a swap is recorded like any other load into the real game.
- System-wide state is not changed without being asked: no layer registration in the registry, no environment variables outside a test's own child process, nothing that an installation into `F:\vulkan` would write outside that folder. The game gets the DLL through the launcher's injection (inject entry), which needs none of that; the launcher's settings are the user's to change. The agent changes a launcher setting only when the user asks for that change on the spot, as on 2026-10-12 for switching the EFMI profile between its DX11 and Vulkan configuration (`d3d11_mode_cmd_args` and `xxmi_dll_inject_mode`): the launcher and the game must not be running, a copy of the file goes to `build/backups/` first, only the named values are touched, and the result is reported. The signed values (injected libraries, custom launch) are never edited.
- Keep "builds", "loads in the sandbox", "captures in the sandbox", "loads in the real game", "data captured in the real game" and "verified on a real character" strictly apart. A sandbox result must not stand in for the real game, and a historical result must not stand in for this round.
- After changing the layer, build what changed and run the shortest checks that cover it: the check that failed before the change and the steps of the area it touches (`sandbox/run_all.py --no-build --only <area>`). Before a deployment, the areas touched since the last one; the whole regression suite only when a change spans most areas (user, 2026-10-26: keep regressions as short as possible, do not spend long times on them). A DLL stays loaded in a process until it exits; a successful build on disk does not mean a running process has the new version.
- Version numbers are three single digits that advance like a counter (user, 2026-10-13): every new version adds one at the rightmost digit, and a digit that reaches ten carries into the one on its left, so 0.9.9 is followed by 1.0.0. No position ever holds 10 or more. The build released as 0.10.0 on 2026-10-13 predates the rule; in the sequence it stands for 0.9.4, and the build after it is 0.9.5.
- Commit after every change (user, 2026-10-11): once a change has passed its verification, review the diff, sync the project memory and create a local Git commit unprompted. No remote is configured; nothing is pushed until the user names a repository. Build output, captures and game assets are not committed.
- Before ending a round of work, update the current state, the tasks and the session log; when there is a new decision or problem, update the corresponding document as well. Record evidence, the scope of verification and what remains; do not paste long logs.
- Everything in this workspace is written in English and contains no Chinese characters: file names, documents, project memory, code comments, test data and commit messages (user, 2026-10-11). A string that has to match text which another tool produces in a different script is spelled with `\u` escapes. `scripts/check_text.py` checks this and is part of the regression suite. Conversation with the user is in Chinese; that concerns the chat only, not the files.
- Windows opened by tests (the sandbox program and the like) go on the secondary screen and do not take the focus (carried over from the EFMI MCP agreement, user, 2026-10-08).
